# Shipped directional statistical-contract audit

Issue [#1351](https://github.com/pedrosakuma/dotnet-diagnostics/issues/1351)
audits the shipped scenario-specific contracts tracked by
[#1348](https://github.com/pedrosakuma/dotnet-diagnostics/issues/1348). The
review uses the four-layer model from
[`statistical-evidence-contract.md`](../design/statistical-evidence-contract.md):
raw evidence, measurement quality, a scenario-specific directional
observation, and a supported next action or explicit abstention.

This is a source audit, not a new statistical framework. It inspected Core,
CLI, MCP, BenchmarkDotNet, the VS Code extension, tests, and English
documentation where each family is intentionally present. It also records
schema, payload, and MCP catalog implications. The audit does not expose a
Core/CLI-only contract through MCP and does not reinterpret old artifacts with
new evidence.

## Audit criteria

The design contract requires a stable quantity ID, unit, aggregation, and
normalization; compatible baseline/current or baseline/candidate semantics;
explicit independence and comparison-axis identity; and separate acquisition
quality, assumptions, and limitations
([`statistical-evidence-contract.md:39-52`](../design/statistical-evidence-contract.md),
[`statistical-evidence-contract.md:133-155`](../design/statistical-evidence-contract.md)).
Loss, truncation, incompatibility, sampling, and insufficient evidence must not
become zero or a directional signal. Intervals and quality measurements are not
problem verdicts, and the next action must follow from the observed quantity
rather than from a generic health label.

## Surface conclusions

- **Core owns calculations.** CLI, MCP, BenchmarkDotNet, and VS Code do not
  independently recompute the audited statistical results.
- **Surface absence is intentional.** GC/LOH and contention concentration remain
  Core/CLI-only. Objective retained growth is Core/CLI plus a CLI-backed VS Code
  lens. Request latency and CPU use the existing MCP comparison envelope. ThreadPool
  uses the existing typed counter-output path. BenchmarkDotNet retains separate
  diagnoser semantics where its benchmark-run evidence differs.
- **Legacy evidence stays legacy.** Missing objective retained-growth blocks,
  missing contention concentration, and missing/unsupported GC pressure schema are
  not synthesized from current defaults. Request-latency and CPU schema mismatches
  are rejected. ThreadPool quality failures make action-relevant fields unavailable.
- **Quality does not become the problem.** Loss, truncation, unresolved symbols,
  incomplete requests, missing lock identity, and irregular counter cadence are
  interpretation gates. They are not evidence that latency, CPU, contention,
  memory, GC, or starvation is itself worse.

## Follow-up decisions

The audit found three independently actionable product gaps:

1. [#1354](https://github.com/pedrosakuma/dotnet-diagnostics/issues/1354)
   versions retained-growth quantity/workload/normalization compatibility before
   pooling repeated process-run deltas.
2. [#1352](https://github.com/pedrosakuma/dotnet-diagnostics/issues/1352)
   implements a versioned, verdict-free MCP heap-growth projection without
   exposing the Core/CLI objective contract through MCP.
3. [#1353](https://github.com/pedrosakuma/dotnet-diagnostics/issues/1353)
   adds explicit queue/worker quantity and unit metadata to the typed ThreadPool
   backlog contract and measures the resulting MCP catalog change.

The remaining findings are compliant behavior or documentation drift corrected
with this audit. Request latency, CPU, GC/LOH, and contention do not justify
speculative implementation issues.
