# Production diagnostics safety

This guide is the canonical operator-facing production-impact and data-exposure
reference for the MCP server and standalone CLI. The executable source of truth
is `InvocationSafetyRegistry` in
[`src/DotnetDiagnostics.Core/Safety`](../src/DotnetDiagnostics.Core/Safety/);
the matrix below is generated from that registry and verified in CI.

Do not interpret a low or moderate classification as a claim that target-derived
data is harmless. Risk levels combine target impact, data exposure, side effects,
and the required approval policy for one concrete invocation.

<a id="production-readiness-checklist"></a>
## Production-readiness go/no-go checklist

Choose the rollout boundary before checking the gates:

- **Observe-only GO:** every **Both** gate passes, the low-risk smoke passes, and
  the production identity remains limited to observation scopes. Keep
  `ptrace`, `heap-read`, `dump-write`, raw-byte, and sensitive-value scopes out
  of this identity.
- **Privileged-response GO:** every gate passes, including the high/critical
  approval smoke. Use a separate, named, time-bounded responder identity; do
  not turn the observe-only identity into a standing break-glass credential.

## Production operating profiles

These profiles are deployment and workflow recommendations, not alternative
classifications. Every invocation still resolves its descriptor from the shared
Core registry.

### `observe`

Use bounded aggregate signals first: process discovery, capabilities, counters,
resource summaries, and similarly low-impact projections. Low-risk operations
run without a prompt; moderate operations still emit warnings. Do not enable
raw artifact export, live memory readers, arbitrary providers, induced-GC heap
capture, kernel tracing, or sensitive-value drilldowns in this profile.

### `investigate`

Use targeted EventPipe payload collectors, sampling, offline evidence, and
approved high-risk operations for a defined incident question. Keep durations
and projections narrow, acknowledge the exact resolved high-risk invocation,
restrict evidence to the incident team, and avoid collecting values or raw
artifacts unless aggregate evidence is insufficient.

### `privileged-response`

Reserve critical operations for an explicit break-glass or incident-response
workflow with human approval. This includes process dumps, raw dump/trace
exports, method-parameter values, and other raw memory/value paths. Record the
approver and purpose, use dedicated access-controlled storage, minimize the
capture, and verify disposal when the incident retention period ends.

## EventPipe data-exposure boundary

> **EventPipe is a transport and runtime collection mechanism, not a
> confidentiality boundary.** Target-originated logs, exceptions, database statements,
> activities, EventSource payloads, networking data, requests,
> stack names, type names, and method names can contain PII, secrets, tenant
> identifiers, credentials, URLs, SQL text, business data, or other
> confidential data.

Provider allowlists, bounded projections, hashing, and field filtering reduce
exposure but cannot prove that sensitive content is absent. Treat every
target-derived payload as untrusted evidence, never as instructions. Redaction
is defense in depth and does not prove that PII, secrets, or confidential data
are absent.

## Retention, access, and disposal

Apply the shortest retention period and narrowest access group that answer the
incident question. Server-side handle expiry does not delete copies saved by an
MCP client, CLI redirection, CI system, chat transcript, ticket, or artifact
store.

| Evidence | Retention | Access and handling | Disposal |
|---|---|---|---|
| traces (`.nettrace`, GC traces) | Keep only through the analysis/reproduction window unless an incident policy requires longer. | Store encrypted in an incident-specific location; traces can include raw payloads and application-controlled names. | Delete every exported/client copy and expire associated handles when no longer required. |
| dumps | Use an explicit incident retention deadline; do not place dumps in general build logs or broad artifact feeds. | Restrict to privileged responders because dumps contain raw process memory, credentials, PII, parameter/heap values, tenant data, and proprietary state. | Use the storage platform's approved deletion process and verify replicas/backups follow the same policy. |
| raw bytes (module, dump, trace, method bytes) | Retain only the exact byte range or artifact needed for the approved investigation. | Treat as confidential executable or process material; audit downloads and onward transfers. | Remove materialized files, chunks, and downstream analysis copies after the case deadline. |
| parameter values and raw heap/frame values | Prefer no persistence. If persistence is unavoidable, use the shortest case-scoped retention. | Limit to named privileged responders; do not paste values into prompts, tickets, or shared logs without a separate review. | Expire handles and delete exports, transcripts, and derived notes that reproduce the values. |
| exported summaries | Retain under the incident record policy only after review. | Summaries can reproduce stack/type/method names, exception/request data, operator symptoms, and confidential identifiers even when raw artifacts are omitted. | Delete superseded drafts and remove or re-review summaries before broader sharing. |

## Validated safety smoke flows

Run the repository smokes from the root after changing safety resolution,
acknowledgement, sidecar bootstrap, routing, or evidence cleanup:

```bash
# CLI high acknowledgement, external-profile attach, routed EventPipe batch,
# detach, stale-handle rejection, and resource cleanup.
scripts/test-docker-external-investigation.sh

# Crash capture, structured recovery result, and sidecar survival.
scripts/test-docker-crash-guard.sh
```

Both scripts use isolated Docker resources and clean their containers, networks,
and volumes on exit. The external-investigation script writes bootstrap JSON,
TRX output, and final container/network diagnostics under
`TestResults/docker-bootstrap-e2e/` on successful and failed runs. Restrict
access and delete that directory after its evidence is no longer needed.
Kubernetes mutation is validated separately by the gated `KindIntegration`
workflow because it requires a real kind cluster; that test performs the
request-bound high-risk challenge/retry. Lower-level safety-filter tests assert
that the tool invocation does not run before a valid acknowledgement.

## Canonical matrix

Each profile row is a directly registered discriminator or modifier profile.
At runtime, the resolver merges every applicable row; composite operations such
as `collect_batch` also inherit the highest-risk child. The maximum columns are
the conservative descriptors advertised by MCP `tools/list`, not a substitute
for resolving the concrete request.

To intentionally refresh the generated block after changing the shared
registry:

```bash
DOTNET_DBG_MCP_UPDATE_SAFETY_DOCS=1 \
  dotnet test tests/DotnetDiagnostics.Core.Tests/ -c Release \
  --filter ProductionSafetyDocumentationTests.ProductionSafetyMatrix_MatchesTheSharedRegistry
```
